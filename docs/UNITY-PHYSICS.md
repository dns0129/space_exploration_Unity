# Unity 物理方案

Unity 在这个项目中的主要价值，是把飞船、人物、地形接触和后续舰内物体纳入同一套成熟的物理与编辑器工具。原版已经有局部米制碰撞和浮动原点，迁移保留这两项设计；仅更换引擎不会自动消除大尺度误差。

## 坐标与模拟

世界数据使用双精度米制坐标，各恒星系统保持各自的参考系。远距离速度积分也使用双精度；跨系统跃迁到达时切换系统参考系，不把光年距离压进 Unity Transform。

近地飞行、人物和地形进入单精度米制局部场景。`ShipController.Origin` 是局部原点，飞船的位置为原点加刚体局部位置。超过 1000 m 后将原点平移，并对船体、人物、地形执行相反平移。速度、角速度和方向不参与平移。

PhysX 由 `VoyagerSimulation` 手动以 1/120 秒推进。顺序是施加飞船/人物输入和重力、运行 `Physics.Simulate`、读取刚体结果、必要时重置原点。渲染帧的长短影响一帧执行多少个固定步，不直接改变力的积分时间；每帧最多处理 0.1 秒，持续低帧率时会减慢模拟，避免无限追赶。

## 力与接触

径向重力使用 `g(r) = g(surface) × (R / max(R, r))²`。地球、月球、火星等参数来自原版；系外行星与虚构航区继续沿用游戏设定，不作为实测质量或真实天体模拟。

辅助驾驶通过有限加速度接近期望速度，松开推力时施加阻尼；关闭辅助时直接施加方向推力，保留侧向惯性并响应重力。大气密度按高度指数衰减，无推力时施加大气阻尼。当前模型是游戏飞行模型，没有气动升力、真实热流或六自由度航天器发动机分配。

远距手动飞行对每个实际天体执行连续的球体路径测试，地形最高包络加安全余量决定转入局部模拟的边界。边界处将速度限制到 1000 m/s，这是防止天文巡航速度进入米制碰撞场景的游戏安全行为，会提前于实际地面 10 km 区域发生。同系统跃迁经过天体安全包络时终止，当前没有自动绕行路线规划。

飞船使用连续动态碰撞和盒体碰撞，人物使用胶囊碰撞与地形支撑查询。地形渲染与 MeshCollider 使用同一批从原高度场采样的顶点；飞行局部网格覆盖约 32 km，徒步局部网格覆盖约 160 m，移动到阈值后重建。当前网格在局部逼近原高度场，不是完整球面的逐三角形等价移植。

## 这个方案的优点

| 优点 | 对本项目的直接价值 |
| --- | --- |
| 接触与惯性更统一 | 船体、地形、人物可使用同一物理引擎；碰撞摩擦、反作用、转动和后续舱内物件不必分别自制解算器。 |
| 更容易调出飞行手感 | 在 Inspector 中调整质量、力矩响应、刹车、步速和跳跃；Scene 视图直接查看碰撞体和接触位置。 |
| 更容易扩展物理效果 | 可以在当前组件上增加关节起落架、悬架、可碰撞残骸和粒子效果，也可接入 Unity 的动画、音频及渲染工具。 |
| 能继续兼顾大尺度与小动作 | 双精度远距导航与局部 PhysX 分工，避免将 AU/光年级坐标直接用于米制碰撞。 |
| 开发工具与桌面发布更完整 | Unity Profiler、Frame Debugger、Test Runner 与桌面构建流程便于定位物理、渲染和资源问题。 |
| 迁移可追溯 | 保留原网页代码，世界和高度场可重新生成，并用原版采样作为对照，便于发现迁移差异。 |

性能改善取决于硬件、场景、资源加载和后续优化，需要 Unity 实机测量；当前没有证据支持固定倍数的帧率提升。Unity 也会增加编辑器安装、包导入、原生构建和平台适配成本，无法保持原来单个 HTML 下载即玩的交付方式。
